## Как я воспроизвожу результат

```bash
.venv/bin/python -m pytest --cov --cov-report=term-missing --cov-report=html:reports/coverage --junitxml=reports/junit.xml -q
.venv/bin/python scripts/mutation_check.py
.venv/bin/python scripts/http_smoke.py
.venv/bin/python scripts/zip_smoke.py
```

Я сохраняю HTML/JUnit в игнорируемом `reports/`. Упаковщик сверяет явный allowlist,
отклоняет приватные пути, контакты, маркеры секретов и symlinks. Он перечитывает
ZIP и сверяет каждый файл с исходником, затем записывает SHA256SUMS. Результат
проверки ZIP и квитанцию опубликованного релиза фиксирую рядом с журналом проекта.

## Какие проблемы я встретил

Я прервал первый прогон в ограниченной среде без результата и повторил с
разрешёнными локальными потоками/сокетами. Это не успешная проверка. Первый
завершённый pytest прошёл с предупреждением об HTTPX; после перехода на HTTPX2
повтор прошёл без предупреждений: 42 passed за 5.75 секунды. Ошибку пути при
подготовке упаковщика я исправил до сборки. В universal lock я включил
зависимости Windows, которые Linux сам не устанавливает.

## Как я различаю локальный результат, CI и публикацию

Локальные результаты выше я выполнил до публикации. В GitHub Actions я настроил
Ubuntu 24.04 / Python 3.12.15 и Windows 2025 / Python 3.12.10. Оба job должны
пройти pytest, мутации, реальный HTTP и ZIP. Публикация релиза зависит от их успеха.
Конкретный запуск и его заключение я смотрю в
[Actions](https://github.com/Decl1s/refund-api-quality/actions), а tag/ZIP/SHA256 —
в [релизе](https://github.com/Decl1s/refund-api-quality/releases/tag/v0.1.0).
Само наличие workflow я не считаю подтверждением выполнения на Windows.

Я не проверял macOS, нагрузку, power loss, сетевую файловую систему, внешний PSP,
авторизацию, интернет-деплой или полный security audit. Секретов, пользовательских
документов и настоящих персональных данных я не использовал.
