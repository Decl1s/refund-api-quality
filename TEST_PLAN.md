# Как я проверяю частичные возвраты

Я начинаю с риска неверной суммы и двойного применения. Основной oracle —
наблюдаемый HTTP-ответ **и состояние после запроса**, а не только код 200.
Каждый обычный тест я начинаю с отдельной временной БД; набор данных фиксирован.

| ID | Мой риск и техника | Что я выполняю | Что я ожидаю | Где я автоматизировал |
| --- | --- | --- | --- | --- |
| QA-01 | Я проверяю основной путь | Заказ 10000, возврат 3000 | 201; остаток 7000, один возврат | `test_partial_refund_contract` |
| QA-02 | Я проверяю точную границу | Возврат ровно 10000, затем ещё 1 | 201, затем 409; остаток 0 | `test_exact_full_refund` |
| QA-03 | Я проверяю повтор | Два одинаковых ключа и тела | 201/200; один refund_id и один факт | `test_repeat_does_not_double_refund` |
| QA-04 | Я проверяю классы конфликта | Старый ключ + другая сумма, валюта или заказ | 409 `IDEMPOTENCY_CONFLICT`; исходный факт сохранён | `test_key_conflicts_with_different_payload` |
| QA-05 | Я проверяю валюту | RUB-заказ, USD-возврат | 409 `CURRENCY_MISMATCH`, без записи | `test_currency_mismatch` |
| QA-06 | Я проверяю отказ и восстановление | 10001 отклонён, затем 10000 с тем же новым ключом | 409, затем 201: отказ не занял ключ | `test_excess_does_not_reserve_key` |
| QA-07 | Я проверяю состояние после серии | 3000 + 7000, повтор первого | 201/201/200; сумма 10000 и два факта | `test_multiple_refunds_and_replay_after_exhaustion` |
| QA-08 | Я проверяю типы и границы | 0, -1, 100000001, дробь, float, строка, bool, null | 422, состояние не изменилось | `test_invalid_amounts` |
| QA-09 | Я проверяю обязательность и формат | Нет ключа, пустой, пробел, 65 символов, не-ASCII | 422, состояние не изменилось | `test_invalid_keys` |
| QA-10 | Я проверяю схему JSON | EUR, нет currency, лишнее поле, обрыв JSON | 422 `VALIDATION_ERROR`, без отражения input | `test_invalid_body_contract`, `test_malformed_json` |
| QA-11 | Я проверяю ресурс и метод | Неизвестный заказ; DELETE | 404; 405 | `test_missing_order_and_wrong_method` |
| QA-12 | Я проверяю ID и денежные края | Неверный ID; сумма 1 и 100000000 | 422 для ID; 201 для допустимых краёв | `test_invalid_order_ids`, `test_order_boundaries` |
| QA-13 | Я проверяю уникальность | Повтор создания заказа с другой суммой | 409, первоначальный заказ не меняется | `test_duplicate_order_preserves_original` |
| QA-14 | Я проверяю сохранность | Новый экземпляр приложения, прежний ключ | 200, тот же refund_id и сумма | `test_restart_preserves_replay` |
| QA-15 | Я проверяю конкуренцию | Два разных ключа по 7000 на заказ 10000 | Один 201, один 409; сумма 7000 | `test_simultaneous_refunds[False]` |
| QA-16 | Я проверяю конкурентный дубль | Два одинаковых ключа по 7000 | 201 и 200; один факт | `test_simultaneous_refunds[True]` |
| QA-17 | Я проверяю временный отказ | Удерживаю writer другой транзакцией | 503 STORE_BUSY, Retry-After=1; без факта | `test_busy_returns_retryable_error` |
| QA-18 | Я проверяю транзакцию | После INSERT вызываю нарушение FK | Вся запись откатывается, следующий writer работает | `test_sql_failure_rolls_back_and_connection_closes` |
| QA-19 | Я различаю ошибки | Выполняю SQL к отсутствующей таблице | Ошибка не маскируется под retryable BUSY | `test_unexpected_sql_error_is_not_reported_as_busy` |
| QA-20 | Я проверяю свойство | 40 генерируемых последовательностей | Совпадение с моделью, 0 ≤ сумма возвратов ≤ оплачено | `test_refund_sequence_matches_independent_model` |

Я отдельно проверяю health/OpenAPI, настоящий HTTP, demo из ZIP и три
контролируемые мутации. Через `pytest -m api`, `-m concurrency`, `-m property`
я выбираю соответствующий уровень. ASGI TestClient не проверяет TCP/Uvicorn;
для этого у меня есть `scripts/http_smoke.py`.

Я не называю этот план полным security, load или E2E тестированием внешнего PSP.
Ручной маршрут и точные тела запросов я оставил в README. Дефект, обнаруженный
на изменённой копии, я маркирую как контролируемую мутацию, а не как инцидент.
